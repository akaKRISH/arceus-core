## Method

`experiments/bench_index.py` creates a fresh temporary directory containing:

- `files` empty files distributed across `dirs` directories, each with a `nested` subdirectory;
- extensions cycled across `txt`, `md`, `py`;
- a SQLite database in a sibling directory, outside the indexed root.

It then:

1. registers the root and times the first scan;
2. rescans to measure idempotency;
3. scans a third time under `tracemalloc` to record the Python-heap peak;
4. runs five searches 50 times each and records median and p95 latency;
5. deletes every tenth file and times a reconciliation scan;
6. checkpoints WAL and records database bytes.

No real user directory is indexed. File contents are never read by the scanner; the benchmark files are empty.

## Interpretation

- The scanner processes roughly 11k–16k files/s on this machine for a warm local SSD tree, with scan time dominated by directory enumeration and SQLite writes. A 10× larger index increased scan time roughly 14×.
- Storage is about 466–490 bytes per entry, consistent with duplicated name/path key columns and indexes. No file content or hash is stored.
- Search latency scales with index size because substring matching uses `LIKE '%…%'` over `name_key`/`rel_key`; there is no FTS table. At 20k entries the median is 12–23 ms. This is acceptable for the current interactive CLI but is an explicit limitation, and the reason FTS/embedding work is deferred until a task benchmark shows it is needed.
- Reconciliation after deleting 2,000 files marked exactly 2,000 rows missing, and an immediate rescan marked zero, which supports idempotency of the scan + reconcile path.
- Python-heap peak is small because entries are written in batches of 500. The measurement excludes SQLite's native page cache and OS file cache.

## Threats to validity / not measured

- Single machine, single run per scan; search timings are 50 repetitions but no confidence intervals are reported for scan time.
- Windows-only. No Linux or macOS measurement.
- Synthetic names and an empty-file workload; antivirus, network drives, and huge files were not exercised.
- No concurrent reader/writer or multiple-process scan test.
- Peak RSS and GPU memory were not measured; `tracemalloc` is a Python-heap proxy only.
- The "no match" query is not a worst case in wall-clock terms because it returns no rows to sort; a broad substring query with sorting is the slower case in these results.

## Reproduction

```powershell
.\.venv\Scripts\python.exe experiments\bench_index.py --files 20000 --dirs 100 --repeats 50
```

Deterministic scan/reconcile correctness is covered by the test suite (`python -m pytest`), including partial-scan retention, directory-cascade deletion, Unicode paths, idempotent rescans, and a check that file contents never reach the database.
